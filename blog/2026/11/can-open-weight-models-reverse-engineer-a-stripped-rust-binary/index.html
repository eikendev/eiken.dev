Can open-weight models reverse-engineer a stripped Rust binary?

ai llm reverse-engineering rust open-weight

I took a stripped Rust binary from a small tool I’ve been maintaining since 2021, handed it to four open-weight models, and asked them to explain how one piece of its logic works. Each model got its own sandbox and had to work alone, without running the binary. I ran each one 3 times. The best model was never wrong. The rest were basically a coin flip, and not one of them ever came back with “I don’t know”.

The binary is fully optimised and stripped (no symbols). Most of the standard library is inlined into a handful of very large functions. This means models have to actually read the code and reason out what it does.

What stood out#

The run-to-run spread inside a single model is bigger than the gap between models. 3/4 models had at least 1x fully correct run and 1x wrong run. One run per model tells you almost nothing.

I know this would deserve more runs, across more questions, and more targets. But it’s sufficient to satisfy my own curiosity for now.

GLM seems to be careful. It never got it wrong, and its one partial answer missed a single detail. It’s also the priciest model, and it hit the step limit twice.

DeepSeek wins on value: roughly a sixth of GLM’s price for a mean of 0.5. Its one bad run burned the whole budget and took 45 minutes. It ran out of steps before finishing and handed in something “rushed”.

Kimi and Mistral quit too early. Their wrong runs finished well inside the budget with a confident wrong answer, while their right runs took longer. It’s not that they can’t do it; they just decide they’re done before they’ve checked.1

No model said “I don’t know”. All twelve runs gave a confident answer, even though the models know a wrong one scores worse than “unknown”.

At least every run found the correct function. The wrong answers all misread what that function does with the data, and they got it wrong in one of the same handful of ways.

How I ran it#

Each run is a single OpenCode agent session inside a Podman container:

  • No network, apart from the model API.2
  • The binary isn’t executable, and the prompt forbids running or emulating it. The harness flags any attempt, and a flagged run is thrown out.
  • Static tools only: the usual binutils, plus a decompiler, a disassembler and a binary analysis framework, each with a short guide.3
  • At most 100 steps (model turns).4

All models went through OpenRouter with zero data retention, at high reasoning effort.

An LLM judge (Gemini 4 Argon) grades each answer against a “solution” I wrote myself.

Caveats#

  • 1x binary, 1x question, 3x runs per model. Read the outcomes here as a tendency: a single lucky or unlucky run would move any model’s mean a lot.
  • The source is public, so a model could in theory know the tool from training. Nothing in the transcripts points that way, and the wrong answers don’t read like recalled memory, but I also can’t rule it out.
  • Everything ran in one harness, OpenCode, with its tool set and its way of counting steps. A different agent harness could change the results.
  • The runs aren’t fully isolated. All containers share OpenCode’s session database, so in theory a run could read an earlier run’s answer. The transcripts show no sign of it, but nothing prevents it.
